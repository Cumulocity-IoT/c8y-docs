This agreement is made between {{< company-c8y >}} ("Provider") and the customer ("Customer") who utilizes the Provider's hosted software solutions and services. The following license metrics define the usage measurements and calculations that form the basis for billing and invoicing of {{< company-c8y >}} services.

These license metrics are valid for December 1st, 2026 onwards.

### Differences from previous versions {#differences-v4}

Version 4 restates the [messages](#messages-v2) definition for clarity, without altering the calculation of the metric. In addition, messages now include the additional messages resulting from DataHub 2.0 usage in excess of the usage quotas. Version 4 further adds the [DataHub 2.0](#datahub2-v4) definition. The [DataHub - GiB of data queried](#datahub-gib-v1) and [DataHub - Memory unit](#datahub-memory-v1) metrics apply to DataHub 1.0 only. In all other respects, version 4 is identical to [version 3](#differences-v3).

### Messages {#messages-v4}

The messages usage metric for a given billing period (calendar month) is determined for each tenant as the maximum of:
1. The total count of all data transactions to and in the {{< product-c8y-iot >}} platform, or
2. the total count of billable messages processed through the MQTT Service, or
3. the total count of MQTT connection-minute equivalent messages.

For tenants that are subscribed to [DataHub 2.0](#datahub2-v4), additional messages can arise from usage of that add-on in excess of its usage quotas. Those additional messages are added to the value determined above, as described in [DataHub 2.0](#datahub2-v4).

A data transaction is defined as any authenticated API request with the intention to create, update, or process data within the {{< product-c8y-iot >}} domain model, including inventory objects, operations, measurements, events, and alarms. Transactions are counted regardless of the processing mode, the details of which can be found in [HTTP usage](https://{{< domain-c8y >}}/api/core/#section/REST-implementation/HTTP-usage). Transactions originate from both internal and external sources, including other {{< product-c8y-iot >}} applications, and are recorded via the platform’s [Usage Statistics API](https://{{< domain-c8y >}}/api/core/#tag/Usage-statistics).

A billable message is an MQTT PUBLISH message published to or received from the MQTT Service, where each 4KiB (4 kibibytes or 4,096 bytes) of message is counted as one message for billing purposes, rounding up to the next 4KiB boundary. For example, a 3KiB PUBLISH message is billed as one message, and a 6KiB PUBLISH message is billed as two messages. The message size includes both header and payload. The system meters the total count of MQTT billable messages daily via the MQTT Service, with each day's count contributing to the cumulative total for the billing period.

A connection-minute is an MQTT client connected to the MQTT Service for one minute. Every 10 connection-minutes equals one billable message. For example, a single MQTT client connected for one hour (60 minutes) counts as six messages, and 1,000 MQTT clients connected for one minute each count as 100 messages. The total count of connection-minutes is metered daily via the MQTT Service, with each day's count contributing to the cumulative total for the billing period.

Platform usage is subject to the quotas listed in [Service quotas](/service-terms/quotas/). Usage that exceeds the listed limits may result in additional charges to ensure platform stability and prevent abuse.

For each billing period and each tenant, the sum of daily MQTT connection-minutes (after conversion to billable messages) count, MQTT billable message count, and the total count of data transactions are separately calculated. The greatest of the three values is used, and any additional messages resulting from usage of [DataHub 2.0](#datahub2-v4) by that tenant in excess of its usage quotas are added. The values of all tenants are summed, and the result is the final invoiced metric, rounded up to the nearest 100,000 units. If one of the values cannot be computed, the other values are used for billing purposes.

#### Examples {#messages-examples-v4}

During a billing period, the sum of the daily values for each of the referenced components of a tenant is as follows:

* Data transactions = **1,192,000**
  * Measurements created = 1,000,000
  * Events created = 20,000
  * Events updated = 5,000
  * Alarms created = 10,000
  * Alarms updated = 5,000
  * Operations created = 1,000
  * Operations updated = 1,000
  * Inventories created = 100,000
  * Inventories updated = 50,000
* MQTT billable messages = **202,000**
  * Inbound billable messages = 200,000
  * Outbound billable messages = 2,000
* MQTT connection-minute equivalent messages = **6,000**
  * Actual connection minutes = 60,000

The total data transactions value is higher than that of the MQTT billable messages or connection-minutes and therefore will be used as the final invoicing metric. To calculate the billable units, the total data transactions is rounded up to the nearest 100,000 units:

_1,192,000 / 100,000 = 11.92_

11.92 rounds up to **12 billable units** of messages for the billing period.

Similarly, in a different billing period the sum of the daily values for each of the referenced components of a tenant is as follows:

* Data transactions = **1,192,000**
  * Measurements created = 1,000,000
  * Events created = 20,000
  * Events updated = 5,000
  * Alarms created = 10,000
  * Alarms updated = 5,000
  * Operations created = 1,000
  * Operations updated = 1,000
  * Inventories created = 100,000
  * Inventories updated = 50,000
* MQTT billable messages = **5,245,000**
  * Inbound billable messages = 5,045,000
  * Outbound billable messages = 200,000
* MQTT connection-minute equivalent messages = **12,000**
  * Actual connection minutes = 120,000

In this case, the MQTT billable message count is higher than the MQTT connection-minutes or data transactions values, so billable messages will be used as the final invoicing metric.
First the billable messages are rounded up to the nearest 100,000 units:

_5,245,000 / 100,000 = 52.45_

52.45 rounds up to **53 billable units** of messages for the billing period.

### DataHub 2.0 {#datahub2-v4}

DataHub 2.0 is an add-on that ingests data from the {{< product-c8y-iot >}} platform into a data lake operated by {{< company-c8y >}}. The add-on is subscribed per tenant. The data lake is provisioned automatically upon subscription, and metering begins on the date the tenant is subscribed.

DataHub 2.0 is invoiced through two existing metrics and introduces no separate billable unit:

* The [Tenant](#tenant-v1) metric, for each tenant that has the add-on deployed.
* The [Messages](#messages-v4) metric, for the usage of the add-on. The add-on is invoiced as an uplift on this metric, which is the single messages value determined as described in [Messages](#messages-v4).

#### Usage quotas {#datahub2-allowances-v4}

Use of the add-on is subject to usage quotas. The quotas are set to cover the standard use of the add-on, and usage within the quotas is included in the subscription. Each subscribed tenant is entitled to the following usage per billing period (calendar month), determined from the messages of that tenant:

| Item                     | Included per tenant | Included per 100,000 billable messages |
| ------------------------ | ------------------: | -------------------------------------: |
| Object store writes      |           4,000,000 |                                 40,000 |
| Object store reads       |          40,000,000 |                                400,000 |
| Egress                   |                   0 |                                0.5 GiB |

An object store write is a request that creates or replaces a file in the data lake, including the requests resulting from the ingestion and the optimization of the Customer's data. An object store read is a request that retrieves a file or its metadata from the data lake, including the requests resulting from queries issued by {{< product-c8y-iot >}} applications and by external query engines.

Egress is the transfer of data out of the object store of the data lake to a region or a cloud provider other than the one in which the tenant is hosted. Data transferred out of other parts of the {{< product-c8y-iot >}} platform is not counted. Data accessed within the same region and cloud provider is not counted.

#### Stored data {#datahub2-storage-v4}

Stored data is the total size in bytes of the raw data location of the data lake, as reported by the object store. The maximum daily value in the billing period is used. Data written outside the raw data location, such as derived or aggregated data sets, is not counted.

The included retention of the raw data is 12 months. Extended retention is activated per tenant for each additional 12 months of retention and is invoiced as an additional uplift on the [Messages](#messages-v4) metric of the current billing period.

The stored data of a subscribed tenant must not exceed 2 KB (2,048 bytes) multiplied by twelve times the billable messages of the billing period, corresponding to one year of data at the message volume of that billing period. For example, a tenant with 1,192,000 billable messages in the billing period has an included stored data volume of:

_1,192,000 x 12 x 2,048 bytes = **29,306,880,000 bytes** (approximately 27 GiB per year of stored data)_

#### Usage beyond the quotas {#datahub2-overage-v4}

Usage in excess of the quotas arises only from atypical usage patterns, such as very large payloads or repeated full scans of the data lake by external query engines. Such usage is converted into additional messages as follows:

| Usage beyond the quota     | Additional messages                                   |
| -------------------------- | ----------------------------------------------------- |
| Object store writes        | 1 message per write                                    |
| Object store reads         | 1 message per 10 reads                                 |
| Stored data                | 1 message per 2 KB (2,048 bytes) above the included volume |

Egress in excess of the quota is not converted into messages. It is invoiced at the actual cost charged by the cloud provider, without markup.

The quotas and any resulting additional messages are determined separately for each subscribed tenant, on the basis of the messages determined for that tenant under [Messages](#messages-v4). The additional messages of all subscribed tenants are added to the messages of the billing period before the rounding described in [Messages](#messages-v4). These additional messages are counted as messages even though no corresponding data was transmitted to the platform.

#### Example {#datahub2-example-v4}

The following example illustrates a tenant whose object store usage exceeds the usage quotas. Standard use of the add-on remains within the quotas and results in no additional messages.

A tenant subscribed to DataHub 2.0 records 1,192,000 messages in the billing period, determined as described in [Messages](#messages-v4), and the following object store usage:

* Object store writes = **5,000,000**
* Object store reads = **30,000,000**

The object store quotas of the tenant are calculated from its messages:

* _Writes included = 4,000,000 + (1,192,000 / 100,000 x 40,000) = **4,476,800**_
* _Reads included = 40,000,000 + (1,192,000 / 100,000 x 400,000) = **44,768,000**_

The reads stay within the quota and add nothing. The writes exceed the quota:

* _Writes above the quota = 5,000,000 - 4,476,800 = **523,200**_
* _Additional messages = 523,200 x 1 = **523,200**_

The additional messages are added to the messages of the tenant:

_1,192,000 + 523,200 = **1,715,200**_

To calculate the billable units, the total is rounded up to the nearest 100,000 units:

_1,715,200 / 100,000 = 17.152_

17.152 rounds up to **18 billable units** of messages for the billing period, compared to 12 billable units for the same messages without a DataHub 2.0 subscription.
